Elevator Pitch

30-45 seconds

Jarvish is a personal AI agent I built to understand modern AI application architecture end to end. The user talks to a React chat interface, the frontend streams a GraphQL subscription over HTTP, and the backend runs a LangGraph state machine. The graph retrieves long-term memory, processes attachments, delegates work to specialized Gemini-powered workers, executes tools like web search, Google Docs, Gmail, Calendar, and local file operations, then streams status, reasoning, and final UI blocks back to the client. It also persists sessions through SQLite checkpointing and stores semantic memory in Weaviate.

Interview framing: This is not just a chatbot. It is a typed, tool-using, stateful agent system with streaming UX, memory retrieval, worker delegation, function calling, persistence, and explicit failure paths.

5 Min Macro Intro

High-level story

Problem

I wanted to learn the real pieces behind AI engineer work: agent state, tool calling, streaming, RAG-like memory, typed frontend/backend contracts, OAuth, persistence, and error handling.

Architecture

The app separates concerns into a React feature, a GraphQL API boundary, a LangGraph orchestration layer, tool services, session storage, and vector memory.

Learning Value

Every part maps to a likely AI engineer interview topic: LLM orchestration, embeddings, retrieval, structured outputs, function calling, observability, auth, and reliability.

Macro answer: The key design choice is separating the conversational UI from the agent execution graph. The frontend does not decide which model or tool to use; it only sends typed input and renders typed streamed events. The backend owns reasoning, tool execution, memory, and persistence.

1:00-2:00 | Product

"From the user's point of view, Jarvish is a chat-based research and productivity agent. The user can start sessions, send messages, attach files, connect to Google services, ask questions about documents or emails, and receive structured answers. The UI can render text, code, data blocks, reasoning blocks, and draft blocks. There is also a ghost-writer panel that opens when the model returns a draft."

2:00-3:15 | Frontend/API Boundary

"The frontend is a React feature under src/features/jarvishAgent. The main component composes three important hooks: Google auth, session management, and chat streaming. When the user sends a message, the chat hook creates an optimistic user message, attaches files as base64, sends a GraphQL request to /graphql, and reads the response as a stream. The API boundary is GraphQL, and I use generated GraphQL types plus Zod validation so the UI is not just trusting random JSON."

3:15-4:30 | Backend Entry

"On the backend, Express hosts GraphQL Yoga. The important operation is agentEvents, which behaves like a streaming agent endpoint. It receives the query, previous history, attachments, session ID, and optionally a Google OAuth token. The resolver calls streamAgentEvents, which creates the LangGraph agent and maps graph updates into UI events like status, reasoning, message, and error."

4:30-6:00 | Agent Graph

"The core of the backend is a LangGraph state machine. The state includes messages, retrieved memories, research notes, attachments, processed attachments, Google token, last worker, tool confidence, and session ID. The graph starts with a context node that retrieves semantic memories, then a processing node that handles attachments and pre-fetches obvious context. After that, a supervisor model decides whether to answer directly or delegate to a specialized worker."

6:00-7:15 | Workers And Tools

"The supervisor can delegate to three workers: research, Google, and coder. The research worker handles web search, pages, PDFs, and uploaded documents. The Google worker handles Gmail, Calendar, and Google Docs. The coder worker handles local files, codebase analysis, drafting, and memory changes. Workers can call tools using Gemini function calling. But the backend still validates every tool argument with Zod before execution, because model output is untrusted."

7:15-8:15 | Memory And Persistence

"The system has two kinds of persistence. SQLite stores application records: sessions, summaries, structured facts, and LangGraph checkpoints. Weaviate stores semantic memory. When a new query arrives, the memory service embeds the query, searches Weaviate, and only passes memories above a relevance threshold. At the end of a run, the archive node summarizes the interaction, extracts facts, indexes attachments, and saves useful context for future retrieval."

8:15-9:15 | Types And Safety

"One thing I focused on is contracts between layers. GraphQL gives compile-time contract safety for API data. Zod gives runtime safety for untrusted data like streamed events, model output, resolver inputs, and tool arguments. Drizzle gives typed database rows. LangGraph gives typed agent state. I also moved the Jarvish UI block protocol into a shared in-repo Zod contract, so frontend rendering and backend model-output validation use the same schema instead of parallel definitions."

9:15-10:00 | Tradeoffs And Close

"The project is intentionally learning-oriented, so I can also explain what I would harden before production. I would move OAuth tokens out of localStorage, add explicit approvals for write tools, isolate users and vector namespaces, add better tracing and evals, protect against prompt injection, and improve schema ownership. The value of the project is that it gave me hands-on experience with the real building blocks of AI engineering, not just prompt writing."

Memory trick: Remember the order as Why -> Product -> Frontend -> Backend -> Graph -> Tools -> Memory -> Types -> Tradeoffs. If you forget details, return to that spine and keep going.

Runtime Flow

End to end
1. User submits

JarvishAgent.tsx creates a session when needed, then calls sendMessage(sessionId).

2. Frontend state

useJarvishChat.ts adds the user message, clears status logs, sets stage to prepare, and opens an abort controller.

3. GraphQL request

The hook posts AgentChat to /graphql with query, history, attachments, session ID, and optional x-google-token.

4. Yoga resolver

agentEvents.subscribe reads the Google token from headers and calls streamAgentEvents.

5. LangGraph stream

The backend creates a graph with a SQLite checkpointer and streams updates from each node.

6. Graph nodes

Context retrieves memory, processing handles attachments and shadow tools, supervisor delegates or answers, workers call tools, archive persists.

7. Event mapping

Node metadata becomes status events. Streamable messages become message; internal node output becomes reasoning.

8. UI rendering

The browser reads the streamed response line by line, validates with Zod, parses JSON blocks, and renders text/code/data/draft/action blocks.

React UI -> GraphQL Yoga -> streamAgentEvents -> LangGraph -> context -> processing -> supervisor -> worker -> tools -> worker -> supervisor/archive -> streamed AgentEvent -> parsed UI blocks

Types And Contracts

Important interview point

Type safety in Jarvish is layered. GraphQL is the main frontend/backend API contract, shared Zod schemas own the UI block protocol, Zod protects runtime boundaries, LangGraph types describe agent state, Drizzle types describe database rows, and service interfaces describe infrastructure boundaries. The important interview point is that each type system protects a different failure mode.

The backend owns the GraphQL schema in src/Backend/graphql/schema.ts, and the frontend uses GraphQL Code Generator to produce typed operations under src/features/jarvishAgent/graphql/__generated__. That means query variables and response shapes like sessions, summaries, facts, message history, and agent events are not hand-written on the frontend.

Boundary Main Types / Files What It Protects Production Improvement
Frontend chat state Message, Attachment, AgentMessageBlock, ChatState UI rendering, optimistic updates, status, attachment handling, and block parsing. Keep UI-only types separate from API and agent-state types.
GraphQL API shapes Backend schema + generated frontend TypeScript operations. Queries, mutations, variables, sessions, facts, history, and agent event payloads. Keep codegen in CI so schema drift fails the build.
Server resolver types src/Backend/graphql/__generated__/resolvers-types.ts types resolver args, return values, and schema models. Backend resolvers stay aligned with the GraphQL schema. Make sure backend codegen runs whenever schema.ts changes.
Server input validation src/Backend/graphql/schemas/resolver.schema.ts validates resolver inputs with Zod. Runtime rules such as min/max/defaults, not just compile-time field shape. Avoid duplicating too many rules between GraphQL and Zod without a clear reason.
Stream/runtime validation Frontend uses parseAgentEventPayload with Zod after receiving streamed data. Malformed streamed events, unexpected backend output, and partial model-generated content. Keep unknown only at the transport boundary, then narrow immediately.
UI block protocol src/shared/jarvish.blocks.ts defines text, code, data, reasoning, action, document, and draft blocks. Predictable rendering of model output as structured UI, with one schema shared by frontend and backend validation. For a larger repo, graduate the shared module into a versioned contracts package.
Tool arguments Backend Zod schemas validate model-generated tool args before execution. Dangerous or malformed model output before it reaches real services. If tools are ever exposed to the frontend, generate client-facing tool types from the same schemas.
Agent state types AgentState defines LangGraph channels; AgentStateType describes state inside nodes. Node-to-node state: messages, memories, attachments, token, confidence, and session ID. Keep reducers and defaults obvious, because incorrect state merge behavior is hard to debug.
Database row types Drizzle exports inferred types like Session, NewSession, StructuredFact. Database reads/writes are typed from table schema instead of manual interfaces. DB types should still be mapped to API types instead of leaking internal row shape everywhere.
Service interface types IVectorStore defines the memory store contract; services hide Weaviate, Google APIs, and file details. Infrastructure boundaries, swappable implementations, and easier tests with mocks or fakes. Add explicit return types on more service functions to make boundaries clearer.
Shared constants src/shared/jarvish.constants.ts holds roles, statuses, event types, block types, tool names, and endpoints. Magic strings across frontend, backend, GraphQL, Gemini, LangChain, and UI rendering. Some role naming is still mixed across UI, GraphQL, Gemini, and LangChain.

Production Pattern

I would create a dedicated shared contracts layer, for example src/shared/contracts or a workspace package like @jarvish/contracts. It would own event types, block schemas, role mappings, and possibly Zod schemas. Frontend and backend would import from it instead of redefining the same structures.

Best Interview Framing

"GraphQL gives me compile-time contract safety for API data, while Zod gives me runtime safety for untrusted data like LLM output and streamed events. On the server, generated resolver types, Drizzle inferred types, LangGraph state types, and service interfaces protect different boundaries. The main improvement is to remove duplicate block schemas and centralize shared contracts."

Agent Graph

LangGraph orchestration

createAgentGraph builds a StateGraph from AgentState, registers each node, adds topology, then compiles it with an optional SQLite checkpointer. The state machine gives the app resumable, inspectable execution instead of one large unstructured LLM call.

Context

Embeds the latest query and retrieves top relevant memories from Weaviate.

Processing

Extracts attachments with Gemini and predicts obvious tools like web search or file read to pre-fetch context.

Supervisor

Uses Gemini with function declarations to delegate to research, Google, or coder workers, or to synthesize final UI blocks.

Workers

Specialized Gemini prompts with narrower tool sets: research, Google Workspace, and local code/drafting.

Tools

Executes validated tool calls, appends ToolMessage results, scores confidence, and routes back to the last worker.

Clarification

If confidence is below 70, asks the user for missing information instead of guessing.

Archive

Summarizes the session, extracts structured facts, indexes attachments, and stores memory for future retrieval.

Tools

Function calling

Tools are how the agent leaves pure text generation and interacts with real systems. In Jarvish, the model can request a tool, but the backend owns validation, execution, confidence scoring, and routing after the result comes back.

Memory And Persistence

RAG concepts

Jarvish has two persistence tracks: relational state for sessions and summaries, and semantic memory for recall. The important distinction is that SQLite/Drizzle is for exact application records, while Weaviate is for similarity search over meaning.

Semantic memory

addMemory embeds text with gemini-embedding-001 and stores vectors in Weaviate with JSON metadata.

Retrieval

retrieveMemories embeds the query, searches top K memories, then filters by a relevance threshold of 0.65.

Session state

LangGraph checkpoints store graph message history per thread_id, while Drizzle stores user-facing session rows and summaries.

Memory Type Storage When It Is Used Risk
Raw graph history LangGraph SQLite checkpoints Loading previous session messages and continuing a thread. Can grow large; needs pruning or summarization strategy.
Session metadata Drizzle sessions Sidebar list, active session, search, updated timestamps. Must become user-scoped before multi-user production.
Session summary Drizzle session_summaries Fast preview of what happened in a session. Model summaries can be incomplete or wrong.
Structured facts Drizzle structured_facts Profile-like facts extracted from conversations. Facts need provenance, confidence, and user correction.
Semantic memories Weaviate vectors Retrieving relevant prior context for a new user query. Can pollute prompts if irrelevant memories pass the threshold.

Technology Quick Summary

What, pros, cons, alternatives
Technology What It Is Pros Cons Main Alternatives
React Frontend library for building component-based user interfaces. Huge ecosystem, strong mental model, reusable components, good for interactive chat UI. State can become scattered, performance needs care, app architecture is not enforced. Vue, Angular, Svelte, Solid.
TypeScript JavaScript with static types. Catches mistakes early, improves refactoring, documents data contracts. Types can drift from runtime data, adds build complexity, weak types can give false confidence. JavaScript, Flow, Kotlin/JS, ReScript.
Vite Fast frontend dev server and build tool. Very fast local development, simple config, modern ESM workflow. Some ecosystem plugins assume other bundlers, production details still need understanding. Next.js, Remix, Webpack, Parcel, Rspack.
GraphQL Yoga GraphQL server used as the API boundary. Typed schema, single endpoint, good developer tooling, supports subscription-style streaming. More complex than REST, caching can be harder, manual streaming over fetch is fragile. REST, tRPC, Apollo Server, Fastify Mercurius, gRPC.
GraphQL Codegen Generates TypeScript types and typed operations from GraphQL schema/documents. Reduces frontend/backend contract bugs and improves editor autocomplete. Generated files add noise, codegen must run when schema changes. Manual types, tRPC inferred types, OpenAPI generators, Apollo codegen.
Express Minimal Node.js web server framework. Simple, familiar, flexible, easy to mount Yoga and config endpoints. Unopinionated, async error handling needs discipline, not the fastest option. Fastify, Koa, Hono, NestJS.
LangGraph State-machine framework for agent workflows. Explicit nodes/edges, resumable state, better debugging than one big agent loop. More concepts to learn, graph design can become complex, version churn is possible. LangChain agents, LlamaIndex workflows, CrewAI, AutoGen, custom orchestrator.
Gemini Google's LLM used for reasoning, routing, processing, and embeddings. Strong multimodal support, function calling, good fit with Google ecosystem. Vendor dependency, model behavior can change, cost/latency need monitoring. OpenAI, Anthropic Claude, Mistral, Llama, Azure OpenAI, Bedrock.
Function Calling LLM outputs structured tool calls instead of only natural language. Connects models to real actions, enables deterministic service execution. Tool choice can be wrong, arguments must be validated, side effects need approval. JSON mode, structured outputs, ReAct text parsing, deterministic routers.
Zod Runtime schema validation library for TypeScript. Validates untrusted model/API data, provides inferred TypeScript types. Can duplicate GraphQL schemas, runtime parsing has overhead. Valibot, Yup, Joi, io-ts, TypeBox, JSON Schema/Ajv.
Weaviate Vector database for semantic memory search. Purpose-built vector search, metadata support, local embedded option. Operational complexity, memory quality depends on embeddings and chunking. Pinecone, Qdrant, Chroma, Milvus, pgvector, Elasticsearch vector search.
Embeddings Numeric vector representations of text for semantic similarity. Finds conceptually related memories even when wording differs. Can retrieve irrelevant context, needs thresholds, chunking, and evaluation. Keyword search, BM25, hybrid search, rerankers, knowledge graphs.
SQLite + better-sqlite3 Local relational database and fast synchronous Node driver. Simple local persistence, no server setup, good for learning and single-user apps. Limited for multi-user scale, sync driver can block under heavy load. PostgreSQL, MySQL, Turso/libSQL, MongoDB, Redis for ephemeral state.
Drizzle ORM TypeScript ORM/query builder for database schema and queries. Typed SQL-like API, lightweight, clear schema definitions. Requires migration discipline, less batteries-included than larger ORMs. Prisma, Kysely, TypeORM, Sequelize, raw SQL.
SSE-style Streaming Server streams incremental events to the browser over an HTTP response. Great for token/status streaming, simpler than WebSockets for one-way updates. Manual parsing can be brittle, reconnect/error semantics need care. WebSockets, WebTransport, polling, GraphQL subscriptions over WebSocket.
Google APIs + OAuth Access to Calendar, Gmail, and Docs with user permission. Lets the agent work with private user data and real productivity tools. Security-sensitive, scopes must be minimal, write actions need explicit consent. Microsoft Graph, Slack APIs, Notion API, service-specific integrations.
pdf-parse Library for extracting text from PDF files. Simple way to convert PDFs into searchable text. PDF layout extraction can be messy; scanned PDFs need OCR. pdf.js, Unstructured, Tesseract OCR, cloud document AI services.
How to say it in an interview: "I chose a practical learning stack. React and GraphQL make the UI/API boundary typed, LangGraph makes agent control flow explicit, Gemini provides model and tool-calling capabilities, Weaviate handles semantic memory, and SQLite/Drizzle keep local persistence simple. The tradeoff is that production would require stronger auth, evals, monitoring, and side-effect controls."

Buzzwords Glossary

Quick explanation + usage
Term Quick Explanation How It Is Used Here
LLM Large Language Model. A model that predicts and generates text, code, structured data, and tool calls. Gemini is used for supervisor reasoning, worker responses, attachment processing, summaries, and fact extraction.
AI Agent An LLM-powered system that can reason over state, choose actions, use tools, and produce results over multiple steps. Jarvish is an agent because it retrieves memory, routes tasks, calls tools, asks for clarification, and archives output.
Agent Orchestration The control flow that decides which steps, models, workers, and tools run in what order. LangGraph defines the orchestration with nodes like context, processing, supervisor, workers, tools, clarification, and archive.
Supervisor / Worker Pattern A multi-agent pattern where one coordinator delegates focused tasks to specialized workers. The supervisor delegates to research, Google, or coder workers based on the user intent.
RAG Retrieval-Augmented Generation. Retrieve relevant external context before asking the model to answer. The context node retrieves relevant memories from Weaviate and injects them into the supervisor prompt.
Embeddings Numeric vectors that represent the meaning of text so similar ideas are close in vector space. gemini-embedding-001 converts memories and queries into vectors for semantic search.
Vector Database A database optimized for storing vectors and finding nearest semantic matches. Weaviate stores long-term memory and returns similar memories for the current query.
Semantic Search Search by meaning instead of exact keywords. The memory service can retrieve related past conversations even when the wording is different.
Top K The number of best retrieval results to return. retrieveMemories(query, 5) asks Weaviate for the top five relevant memories.
Relevance Threshold A minimum similarity score required before retrieved context is trusted. The memory service filters results below 0.65 to reduce irrelevant memory pollution.
Context Window The amount of text a model can consider in a single request. The app limits memories, truncates tool notes, and summarizes sessions so prompts do not grow forever.
Tool Calling The model requests a named external function with structured arguments. Workers call tools such as web_search, read_file, search_gmail_messages, and update_google_doc.
Function Declaration The schema given to the model that describes available tools and their arguments. registry.ts defines Gemini function declarations for research, Google, and coder worker tools.
Structured Output Model output constrained to a predictable JSON shape instead of free text. Final answers are expected as UI blocks like text, code, data, and draft.
Runtime Validation Checking real data while the app is running, not only at TypeScript compile time. Zod validates streamed events, session history, block content, resolver inputs, and tool arguments.
Type Safety Using types to catch shape and usage errors during development. GraphQL Codegen, TypeScript, Drizzle inferred types, and LangGraph state types protect different boundaries.
Codegen Automatically generating types or code from a schema. GraphQL Codegen generates frontend operation types and backend resolver types from the GraphQL schema.
Streaming Sending partial results as they are ready instead of waiting for the whole task to finish. The backend streams status, reasoning, message, and error events while the graph runs.
SSE Server-Sent Events. A simple browser-friendly pattern for one-way server-to-client event streaming. The frontend reads data: lines from the GraphQL response and updates the chat incrementally.
Checkpointing Persisting workflow state so execution history can be resumed or inspected. LangGraph uses SqliteSaver with thread_id equal to the session ID.
Long-Term Memory Information stored beyond a single chat turn or page reload. Jarvish stores conversation summaries, attachments, and facts in Weaviate and SQLite.
Hallucination When a model invents facts or answers without reliable evidence. The prompts demand verification, tools provide evidence, and low-confidence tool results route to clarification.
Prompt Injection Malicious or irrelevant instructions hidden inside user-provided or retrieved content. A production version should treat web pages, PDFs, email, and docs as untrusted data, not instructions.
OAuth A permission protocol that lets users grant limited access to external services. Google OAuth gives the agent access to Calendar, Gmail, and Docs through a user token.
Scopes The exact permissions requested in OAuth. The app requests Google read scopes; write tools need stronger explicit consent and matching write scopes.
Observability Logs, metrics, and traces that explain what the system did and why it failed. The project has logging; production should add graph traces, token counts, cost, latency, and tool failure metrics.
Evals Evaluation tests for model behavior, retrieval quality, tool usage, and regressions. Good evals would test worker routing, hallucination resistance, memory retrieval, and tool-call correctness.
Guardrails Rules and checks that reduce unsafe, incorrect, or unwanted model behavior. Zod validation, confidence thresholds, clarification routing, and future write-action approvals are guardrails.
Side Effect An action that changes the outside world, like writing a file or updating a document. write_file and update_google_doc are side-effectful and should require confirmation in production.
Multimodal Working with more than one data type, such as text, images, PDFs, or audio. The processing/archive nodes can handle attachments, including PDFs, text files, and image descriptions.
How to use this section: In an interview, define the term in one sentence, point to exactly where it appears in Jarvish, then mention one production concern. That pattern sounds clear and senior without over-explaining.

Bad Designs To Fix

Be candid
Issue Why It Is Risky How To Explain The Fix
OAuth token in localStorage Access tokens are exposed to XSS and are forwarded from browser to backend. Move to a backend OAuth flow or secure httpOnly session, minimize scopes, and rotate/refresh server-side.
Google Docs write scope mismatch The UI requests documents.readonly, but the backend exposes update_google_doc. Add explicit consent for write scope only when needed, or remove write tool until the permission model is correct.
Google client config path incomplete useGoogleAuth.ts has a placeholder for fetching config, so clientId may never load. Restore the /api/config fetch, validate missing config visibly, and test login as a real user flow.
Tool permissions too broad write_file and Google update tools can create side effects from model-generated calls. Add user confirmation, path allowlists, dry-run previews, audit logs, and policy checks before side effects.
GraphQL subscription over manual fetch parsing The frontend manually parses data: lines, which is fragile for real SSE framing and errors. Use a proper SSE/client subscription transport or a dedicated streaming endpoint with tested framing.
Prompt-heavy orchestration Routing quality depends on natural-language prompts and model behavior. Add deterministic intent classification, eval cases, tracing, and fallback routes for known task types.
Memory can become polluted Archive stores summaries and extracted facts even when model output may be wrong. Store provenance, confidence, timestamps, source type, user confirmation, and support correction/deletion workflows.
Duplicate schemas Frontend block schemas and backend block schemas can drift. Move shared schema/contracts to one package or generate both sides from a single source.
Generated code inside feature folder GraphQL generated artifacts live under the app feature and can obscure reviewed code. Keep generated output clearly isolated and excluded from manual edits/review noise.
Limited observability/evals There are logs, but no structured eval suite for routing, tool use, hallucination, or memory quality. Add golden prompts, tool-call expectations, retrieval metrics, latency/cost tracking, and regression tests.
Mixed naming and legacy constants Names like ROLES.AGENT, assistant, model, reasoning, and legacy node constants increase mapping bugs. Normalize role taxonomy and create one explicit adapter between GraphQL, LangChain, Gemini, and UI roles.

Interview Questions To Practice

Use these aloud

Macro

Why did you use LangGraph instead of one long LLM call?

LangGraph lets me model the agent as explicit steps with shared state: context retrieval, attachment processing, supervision, worker delegation, tool execution, clarification, and archive. A single LLM call is simpler, but it hides control flow and makes retries, persistence, streaming, and debugging much harder.

Where is the boundary between UI state and agent state?

UI state belongs to React: input text, selected session, attachments before send, loading indicators, visible panels, and rendered blocks. Agent state belongs to LangGraph: messages, retrieved memories, processed attachments, tool confidence, last worker, Google token, and session ID. The GraphQL contract is the boundary between them.

How does streaming improve perceived latency?

Instead of waiting for the full agent run to finish, the backend streams status, reasoning, and final message events as graph nodes complete. The user sees progress like memory retrieval, research, and synthesis, so a multi-step task feels responsive and debuggable.

What is the difference between session history, summaries, structured facts, and vector memory?

Session history is the raw conversation from the LangGraph checkpoint. Summaries are human-readable snapshots for the session list. Structured facts are explicit profile-like facts stored in SQLite. Vector memory is semantic recall in Weaviate, used to retrieve relevant past context for future prompts.

Micro

How are model tool calls validated before execution?

Gemini proposes function calls, but the backend does not trust the arguments directly. tool-executor.ts routes by tool name and parses each argument object through a matching Zod schema, such as UpdateGoogleDocToolArgsSchema or ReadFileToolArgsSchema, before calling the service.

What happens when a tool returns low confidence?

Tool output is scored. Empty output, errors, or "no results" reduce confidence. If confidence is below the configured threshold, the graph routes to the clarification node, which asks the user for missing information instead of letting the model guess.

How do you prevent hallucinations in this architecture?

I use several layers: retrieval context, specialized workers, tool-backed answers, source-oriented prompts, Zod validation, shared UI block contracts, confidence routing, and a clarification path. For production I would add evals, citations as structured metadata, prompt injection filtering, and stricter provenance checks before storing memory.

How would you test worker routing and memory retrieval quality?

I would create golden prompts with expected routes: Google tasks should call the Google worker, web tasks should call the research worker, and code tasks should call the coder worker. For memory, I would test embedding retrieval with known facts, measure precision/recall at top K, and add regression tests for irrelevant-memory filtering.

Production

How would you secure OAuth and Google Workspace tools?

I would move token handling out of localStorage and into a backend-managed OAuth flow with httpOnly cookies or server-side sessions. I would request minimal scopes, separate read and write permissions, require explicit user confirmation for write tools, and log every side-effectful action.

What observability would you add for cost, latency, and failures?

I would trace each graph run with session ID, node timings, model name, token counts, tool calls, errors, retry count, and final route. Then I would add dashboards for latency per node, cost per task, tool failure rate, retrieval quality, and user-visible error rate.

How would you handle prompt injection from web pages, files, or email?

I would treat external content as data, not instructions. Tool outputs would be wrapped with provenance, dangerous instructions would be filtered or marked untrusted, and the system prompt would tell workers never to follow instructions found inside retrieved documents. Sensitive tools would still require policy checks and user approval.

How would you migrate from a learning app to a multi-user product?

I would add real authentication, tenant-aware database rows, per-user vector namespaces, permission checks on every resolver and tool call, rate limits, audit logging, encrypted secrets, background jobs for long tasks, and a proper deployment setup with monitoring and rollback.

Your honest answer

"I built some pieces in a learning-first way, so I can explain the architecture and also explain what I would harden: auth, permissions, schema ownership, evals, prompt-injection defense, and side-effect approvals."
